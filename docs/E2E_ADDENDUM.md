# E2E Addendum — Phase 3c (спека, не код) · v1.0 · 2026-11-19

Дополнение к `COMBAIN_BACKEND_TZ.md`. Ядро — **MLS (RFC 9420)**, а не самописный double ratchet.
Спека рождена тактом «мировые тренды → эмерджентное → интеграция»; принципы см. `hologram/repo/PRACTICES.md`.

## 0. Решения (Q-таблица)

| Q | Тема | Решение |
|---|------|---------|
| Q1 | Ядро протокола | **MLS RFC 9420** (IETF): TreeKEM, PFS + PCS (post-compromise security) из коробки, группы масштабируются O(log n). Не изобретать свой шифр — мир уже съел эти грабли. |
| Q2 | Библиотека | **ts-mls** (TypeScript, RFC 9420, работает в браузере и Node без сборки — наш клиент статический ESM). Fallback: OpenMLS (Rust) через WASM, если ts-mls не дорастёт до interop. |
| Q3 | Пост-квант | **Гибрид** (классика + ML-KEM), как PQXDH у Signal — консервативная норма 2024–2026. В MLS это выбор ciphersuite; спека резервирует поле, включаем ciphersuite с гибридным KEM, как только библиотека даст его стабильно. |
| Q4 | Multi-device | **Каждое устройство = лист в MLS-дереве.** Ключи устройств, не «ключи аккаунта». Устройство добавляется/удаляется commit'ом — членство и есть ACL. |
| Q5 | Бэкапы | Сервер (и Litestream-реплики) хранит **только опак-тексты**. Ключи — только у клиентов. Эмерджентное следствие: бэкапам разговоров «безопасно теряться» — E2E и бэкап-практика смыкаются. |
| Q6 | 1:1 vs группы | **Один механизм**: 1:1 = MLS-группа из двух листьев (путь MIMI/interop), отдельного «приватного протокола» нет. |
| Q7 | Сервер | Сервер — **глухая почта**: хранит и рассылает опак-байты (commits, welcome, ciphertext). Семантика доставки не меняется — те же envelope'ы, что сейчас. |

## 1. Schema (дополнение к §4 ТЗ)

| Таблица | Поля | Заметки |
|---|---|---|
| `Device` | `id, userId, mlsIdentityKey, label, createdAt, revokedAt` | identity-ключ устройства публикуется при привязке; отзыв = удаление листа из дерева |
| `Room` | `+ mlsGroupId, mlsEpoch` | группа MLS 1:1 с комнатой; epoch растёт с каждым commit |
| `MlsState` | `roomId, epoch, ratchetTree(blob)` | серверное состояние дерева — опак, нужен только для доставки welcome новичкам |
| `Message` | `+ isE2E (bool)` | `type='mls'`, `text` = base64 MLSApplicationMessage; поиск/превью по E2E-сообщениям на сервере невозможны — клиентские индексы |

## 2. WS-сообщения (дополнение к §9 ТЗ)

| Тип | Payload | Сервер делает |
|---|---|---|
| `mls_commit` | `{ roomId, commit(opaque) }` | кладёт в MlsState, рассылает `mls_commit` комнате |
| `mls_welcome` | `{ roomId, welcome(opaque), toUserIds[] }` | точечная доставка новичкам (группы до 50 листьев — лимит WS-доставки) |
| `mls_message` | `{ roomId, ciphertext(opaque) }` | как обычное сообщение: persist + fanout + идемпотентность `clientMessageId` |

Сервер не расшифровывает ничего; rate-limit и лимит 500 messageIds — те же.

## 3. Фазы исполнения

| Фаза | Что | Граница |
|---|---|---|
| 3c-1 | Device-management: ключи, UI привязки/отзыва, `Device` в API | без шифрования |
| 3c-2 | E2E для 1:1 (MLS-группа из 2 листьев), клиентские индексы поиска | группы ещё plaintext |
| 3c-3 | E2E для групп-комнат | весь текст опак |
| 3c-4 | Гибридный PQ ciphersuite (ML-KEM) | после стабилизации в ts-mls |

## 4. Честные границы (не скрываем)

- **Метаданные доставки** (кто, кому, когда, размер) остаются видимыми серверу — MLS их не прячет. Сокрытие метаданных — не цель Phase 3c.
- **Бэкап устройства** — вне скоупа: потерял устройство без экспорта ключей = потерял историю (PCS вернёт безопасность в будущее, не прошлое).
- **Звонки** (SRTP/DTLS-SRTP) — отдельный аддендум, как и было.
- Сервер остаётся обязанным: антиспам-лимиты, файлы (вне E2E в 3c), удалить сообщение = сервер удаляет опак-байты; у клиентов оно может остаться до epoch-обновления.
